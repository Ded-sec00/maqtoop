# تحقق سجل نسخ المسودة والمقارنة

28 نوفمبر2026 — الفرع المحلي codex/catalog-revision-history منmain/9adb6d7. النطاق R03 والمرحلةA، بيانات مصطنعة ومحركPostgreSQL16.16 وخادمHTTP علىloopback، دون مزود دفع خارجي أو نشر أو ترحيل إنتاج.

## الدليل الفعلي

أضيفت catalog-history-http إلى84 حالة سابقة. الاختبار الأول بدأPostgreSQL ثم فشلGET السجل404 قبل إضافة المسارات. بعد التنفيذ تمر القراءة والمقارنة عبرHTTP بدوريLOGIN محدودين للإدارة والتاجر؛ مشغل القاعدة يستخدم للتهيئة ورصد الأقفال والمقارنة فقط.

- رُفعت صورتان خاصتان عبرHTTP، ثم أنشأ التاجر النسخة1 وأرسلها للمراجعة. طلبت الإدارة توضيحًا، ثم عدل التاجر المحتوى والصورة عبرPATCH فظهرت النسخة2. السجل يربط ملاحظة الإدارة بالنسخة1، ويعرض محتواها الأصلي ومحتوى النسخة2 دون تعديل تاريخ سابق.
- المقارنة1→2 ترجع اختلافmodel/ramGb/description/mediaAssetIds/proposedWarranty، والصورة المضافة والمحذوفة.2→1 تعكس القيم والصور؛1→1 فارغة. لا تغيير لسعر أو ضمان معتمد؛ النص المقترح للتاجر يظل غير معتمد.
- الإدارة تقرأ النتائج نفسها، بينما التاجر الآخر وزميل المنشأة ولو مُنح الفرع، والعميل والمندوب والخدمة مرفوضون403. مسارadmin يرفضmerchant والعكس. الجلسة الغائبة401، والسجل أو النسخة المفقودة404 بعد التحقق المناسب، والمعاملات الزائدة والمكررة والأرقام غير الصحيحة400.
- يولد مشغل الاختبار نسخًا إضافية كـfixture حتى108، وتقرأ عبرHTTP في7صفحات بحجم17 دون فقد أو تكرار. الإنشاء والتعديل المعتادان عبرHTTP مختبران منفصلًا؛ لا ادعاء تنفيذ106تعديلاتHTTP.
- يحتجز اتصال مستقل صف المسودةFOR UPDATE، وتثبت مراقبةPostgreSQL أن طلبات القائمة وقراءة النسخة والمقارنة الثلاثة تنتظر القفل. تسحب الإدارة الفرع عبرHTTP قبل تحريره؛ ترفض الطلبات الثلاثة403 بلا محتوى. الإدارة تظل قادرة على قراءته، وصورة النسخة القديمة ترفض لصاحب الصلاحية المسحوبة وتتاح للإدارة.
- تمسك عملية سحب إدارية قفل التفويض قبلCOMMIT، وتنتظرها العمليات الثلاث. بعد تثبيت السحب ترجع جميعها403. لا اعتماد على تحقق الجلسة أو الفرع قبل الانتظار.
- خروج التاجر من جميع الأجهزة أثناء انتظار المقارنة يؤدي إلى401 للجلسة القديمة؛ دخول جديد ينجح. إيقاف المدير وإعادة تفعيله أثناء انتظار قراءة نسخة يؤدي إلى401 لجلسته القديمة، ودخول جديد يعيد القراءة.
- قراءة مقارنة مخولة تمسكSHARE قبلCOMMIT ويبدأ كاتبPATCH عبرHTTP. يثبت رصد القفل انتظار الكاتب؛ ترجع القراءة currentRevision=108/version=110، ثم ينشئ الكاتب النسخة109، وتراها قراءة جديدة. لا اختلاط للمحتوى القديم بالنسخة الجديدة.
- قارئDTO الخاصSTABLE، والنسخ والقرارات غير قابلة للتعديل أصلًا. مقارنة صفوف المسودة والنسخ والقرارات والصور وسجل التدقيق ونتائج عمليات المحتوى تثبت عدم كتابةGET. تستثنى من المقارنة عمليات التفويض المقصودة، وتفصل عنها كتابةPATCH المقصودة في تجربة الكاتب المتزامن.
- تقارنfixture جميعsku/stock/offer/quote/hold/payment/purchase_order/order_item/payable/journal/posting وeligible_offer قبل المسارات وبعدها؛ لا أثر على المخزون أو المال. approve ما زال409/CATALOG_POLICY_NOT_CONFIGURED وقائمة العميل فارغة وpublicationEnabled=false.
- ترحيلةcatalog_history.sql الفاشلة بخطأ1/0 قبلCOMMIT تزيل دالتيها وتحفظ البيانات السابقة؛ السليمة تضيف الدوال فقط. لاPUBLIC EXECUTE ولا صلاحية جداول مباشرة للتطبيق. هذا ليس اختبار نسخ/PITR أو قبول إنتاج.

## تشخيص المشغّل وإصلاحه

احتفظت جلسة المراقبة داخل معاملة مفتوحة بلقطة قديمة لـpg_stat_activity، فظهر اتصال واحد بدل الثلاثة الجديدة. أضيفpg_stat_clear_snapshot قبل الرصد، مع تتبع مباشر ومتعدٍ لـpg_blocking_pids؛ أظهرت اللقطة المحدثة الطلبات الثلاثة تنتظر فعلًا.

أدى تراكم رسائلSQL السلبية إلى تعليق إحدى جلساتPostgreSQL بينماrun-tests.mjs ينتظرspawnSync؛ لم تستطع حلقة أحداث الأب تفريغ قنوات سجل المحرك. استبدل تشغيل الأطفال بـspawn غير متزامن متسلسل، فاستمرت قراءة القنوات ونجحت حالات الرفض نفسها دون تغيير كود صلاحياتها. لم تخفض سجلاتPostgreSQL أو تختصر الاختبارات أو تزيد مهلة60ثانية. الخرج محدود1MiB، وأي خطأ تشغيل أو مهلة أو خرج زائد يفشل الحالة حتى لو وُجد دليلJSON سابق.

سجل مراحل الاختبار علىstderr يساعد تشخيص الفشل، ولا يضاف إلى دليل النجاح. عند فشل حالة التاريخ تنظف اتصالاتLOGIN المصطنعة المملوكة لها داخل قاعدة الاختبار الحالية فقط؛ لا اتصال إنتاج أو دور خارجfixture. الطلبات الفاشلة تبقى فاشلة ولا يعوض التنظيف نتيجتها.
