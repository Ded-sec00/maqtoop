# تحقق المرحلة A للكتالوج عبر HTTP وPostgreSQL

27 نوفمبر 2026. النطاق هو المسودات والتفويض والمراجعة الداخلية والصور الخاصة. لا اعتماد نشر أو بيع منتج جديد من الكتالوج؛ حساب7291 وسياسة السعر والضمان لم تتغير.

## طريقة التحقق

يشغل `node scripts/ci/run-tests.mjs` PostgreSQL16.16 معزولًا بقاعدة جديدة لكل حالة، ثم خادم HTTP فعليًا. أضيفت ثلاث حالات catalog-http وcatalog-http-reply-before وcatalog-http-reply-after فوق77 حالة سابقة. لا تستبدل صور/مراجعات وهمية دليل قاعدة البيانات؛ الصور مصطنعة لتجنب بيانات خاصة، لكنها ترفع وتتحقق وتسترجع عبر HTTP فعلي وcodec حقيقي.

تفحص catalog_drafts.cjs حسابات وأدوار LOGIN محدودة مستقلة للتاجر أ والتاجر ب والعميل والمندوب والإدارة ومراجع إداري آخر والخدمة، إضافة إلى بوابة المصادقة. الدخول وتغيير كلمة المرور والخروج من الجميع وإيقاف/إعادة تفعيل الحساب تمر عبر HTTP. تفويض الفرع يهيئه/يسحبه مشغل الاختبار كما يهيئ صلاحيات البنية، وليس العميل.

## ما أثبتته حالات الكتالوج

- فشل ترحيلة مصطنع قبل COMMIT يعيد schema والقيود إلى الحالة السابقة، ثم تثبت الترحيلة الصحيحة دون تغيير بيانات شراء موجودة. هذا اختبار ترحيلة معزولة وليس اختبار استعادة إنتاج.
- رفض merchantId/rate/salePrice/state ومسار التخزين المرسل من العميل، والفرع غير المخول حتى داخل منشأة التاجر، والمستعمل والكميات غير الصحيحة.
- طلبا إنشاء HTTP لنفس المفتاح يرجعان نفس201 ومسودة واحدة، وتغيير البيانات بنفس المفتاح409.
- إرسال نسخة للمراجعة ثم طلب تعديلات ينشئ قرارًا تاريخيًا، وتعديل التاجر ينشئ revision جديدة؛ النسخة أو الحالة القديمة مرفوضة.
- approve يرفض409/CATALOG_POLICY_NOT_CONFIGURED، ولا ينشئ حالة approved أو مخزونًا أو عرض بيع. قائمة العميل فارغة مع publicationEnabled=false.
- قائمة pending_review تتصفح أكثر من100 طلب عبر cursor في صفحتين، مع100 مسودة غير مرسلة خارج القائمة، دون فقد معرف أو تكراره.
- تغيير كلمة المرور والخروج من الجميع والإيقاف/إعادة التفعيل أثناء انتظار قفل المسودة ترفض الجلسة القديمة401 دون قرار. سحب تفويض الفرع يرفض الطلب المنتظر403.
- سحب التاجر عبر HTTP يأخذ القفل ثم يسبق قرار مراجعة منتظرًا؛ ينجح السحب ويرفض القرار القديم409. وقراران مختلفان من الإدارة يتنافسان بقفل مرصود: واحد200 والثاني409 وقرار واحد.
- فشل اتصال HTTP بعد إنشاء أو قرار قبل COMMIT وبعده، ثم إعادة نفس الطلب من جهازين: نفس نتيجة النجاح، وقرار/نتيجة تدقيق واحدة. رُصد انتظار قفل بين إعادتَي القرار، لا مجرد تأخير زمني.
- JPEG/PNG صحيحتان تقبلان، ويسترجع المالك أو المدير bytes الأصل نفسها مع nosniff/no-store وattachment. يرفض العميل والتاجر الآخر؛ وتُرفض الصور المتنكرة والمبتورة والحجم الزائد وحد البكسلات وربط صورة تاجر آخر.
- لا SELECT مباشر للتطبيق على جداول الكتالوج ولا UPDATE مباشر لمخزون الشراء. سجلات النسخ والقرارات والتدقيق والأصول غير قابلة للتعديل عبر واجهات التطبيق.
- طابقت صفوف sku/stock/offer/quote/hold/payment/purchase_order/order_item/payable/journal/posting وeligible_offer حالتها قبل جميع عمليات الكتالوج. لم ينشأ قيد أو مستحق أو مخزون بسبب المسودة أو المراجعة.

البيانات الجماعية المولدة بـSQL في اختبار الصفحات fixtures لاختبار حجم قائمة المراجعة، وليست ادعاء أن كل هذه المسودات أُنشئت عبر HTTP؛ المسار المعتاد للإضافة والقرار والإعادة مختبر عبر HTTP منفصلًا.

## المراجعة والتوافق

المراجعة المستقلة وجدت مشكلة قائمة أول100سجل وغياب اختبار فقد رد القرار، وعولجتا قبل القبول النهائي. راجعت الإصلاح ولم تبق مشكلة مؤكدة ضمن النطاق. تفاصيل القرارات التقنية في [سجل التنفيذ](CATALOG_A_LEDGER.md)، والعقد في [CATALOG_API](../design/CATALOG_API.md).

الصورة الخاصة مخزنة bytea في قاعدة البيانات لهذه الشريحة. لا يوجد نشر صور أو معالجة علامة مائية للعميل أو مخزن إنتاج خارجي. الاعتماديات مثبتة في lockfile، بما فيها sharp0.35.5 للتحقق من JPEG/PNG. لا يمثل هذا تحميلًا تشغيليًا أو قبول ضمان/سعر أو تطبيقًا كاملًا لدليل الحسابات.

النتيجة المحلية النهائية: `node scripts/ci/run-tests.mjs` خرج0 مع80/80 حالة ناجحة على PostgreSQL16.16، تشمل77 سابقة وثلاث حالات الكتالوج. أثبتت كل حالة صفحات مراجعة2 و105 طلبات معلقة بالضبط، ونجاح حماية الصور والتفويض وعدم تغير المخزون أو المال. نجحت اختبارات الحارس15/15 وفحص صياغة18 ملفJavaScript. الأدلة التفصيلية في [results.json](../../db/first_purchase/results.json). نتيجة GitHub تربط بطلب المراجعة بعد رفع هذه النسخة، ولا تستنتج من الاختبار المحلي.
