# عقد إدارة صلاحيات الفروع

27 نوفمبر 2026 — امتداد R03 ومسودات الكتالوج. تستخدمه إدارة Windows عبر API مشترك؛ لا واجهة ويب ولا إنشاء حساب أو فرع من هذه المسارات.

## الإعداد والتوافق

تثبت branch_permissions.sql مرة واحدة بعد catalog_drafts.sql، وتبقى مساراته خلف catalog.enabled=true. الترحيلة إضافية: تحفظ التفويضات الحالية active=true/version=1، وتضيف سجل تدقيق ثابتًا. لا تنشئ بيانات شراء أو تعدل مخزونًا أو مالًا. أدوار التطبيق لا تقرأ جدول principal_branch ولا تعدله مباشرة.

يمنح المشغل EXECUTE لدور LOGIN الإداري المحدود على الدالتين فقط، بالإضافة لصلاحيات الحسابات القائمة:

```sql
grant execute on function purchase_api.branch_access_read(text,jsonb,text) to example_admin_login;
grant execute on function purchase_api.branch_access_write(text,jsonb,text,text,text) to example_admin_login;
```

example_admin_login اسم توضيحي، وليس دورًا تنشئه الترحيلة. لا grants إلى PUBLIC. حتى إذا أخطأ المشغل بمنح EXECUTE لدور آخر، ترفض الدالتان أي جلسة لا تحمل دور admin الحالي. لا يلزم تغيير DTO المسودة أو العميل أو المندوب؛ التاجر يتأثر بفحص التفويض الحالي فقط، والإدارة تضيف أدوات المنح والسحب في تطبيقها الأصلي لاحقًا. لا عميل Dart أو شاشة منفذة في هذا التغيير.

## العرض

GET /v1/admin/accounts/{accountId}/branches

Bearer مطلوب. accountId UUID لحساب merchant؛ منشأته تستخرج من القاعدة. تعرض القائمة جميع فروع منشأته، بما فيها غير المفوضة، حتى100 عنصر بترتيب branchId التصاعدي. المؤشر ?cursor={branchId} موجب؛ لا معاملات أخرى. branchId نص bigint لتجنب فقد الدقة في التطبيقات.

```json
{
  "accountId": "00000000-0000-4000-8000-000000000001",
  "items": [{"branchId": "2", "active": false, "version": 0}],
  "hasMore": false,
  "nextCursor": null
}
```

النسخة0 تعني عدم وجود قرار سابق. صف السحب يبقى inactive ولا يحذف، فيحفظ النسخة. القائمة تصف الحالة الحالية؛ التصفح أثناء تعديلات متزامنة لا يعد snapshot تاريخيًا واحدًا.

## المنح والسحب

POST /v1/admin/accounts/{accountId}/branches/{branchId}/grant

POST /v1/admin/accounts/{accountId}/branches/{branchId}/revoke

Bearer وIdempotency-Key إلزاميان. JSON بالحقول التالية فقط:

```json
{"expectedVersion": 0, "reason": "تكليف موظف التاجر بإدارة هذا الفرع"}
```

expectedVersion عدد صحيح من0 حتى999999999، وreason نص غير فارغ حتى2000حرف. لا يقبل role أو merchantId أو login أو معرفات accountId/branchId في الجسم. يستخرج الحساب والفرع من المسار وتتحقق ملكية الفرع من القاعدة. يعيد النجاح200:

```json
{"accountId":"00000000-0000-4000-8000-000000000001","branchId":"2","active":true,"version":1}
```

كل أمر جديد مقبول يزيد النسخة حتى إذا لم تتغير active. المنح الجديد لحساب/هوية موقوفة مرفوض؛ السحب يظل متاحًا للحساب الموقوف. استرجاع نتيجة أمر قديم لا يمنح صلاحية من جديد. كل نجاح جديد يسجل المدير والحساب والفرع والسبب والنسختين والمفتاح والوقت في catalog.branch_access_audit ضمن المعاملة نفسها.

نطاق منع التكرار هو المدير/العملية/الحساب والفرع/المفتاح. نفس المفتاح والبيانات يعيدان نتيجة الأمر الأصلية دون تطبيقه مجددًا؛ تغير البيانات بنفس المفتاح409. مثال: منح v1 ثم سحب v2 ثم إعادة مفتاح المنح القديم يعيد استجابة v1 الأصلية، لكن الصف يبقى inactive/v2؛ يجب قراءة القائمة لمعرفة الحالة الحالية. مفتاح جديد بنسخة قديمة409، فلا يعيد تفعيل التفويض. أمران مختلفان بنفس النسخة يتسلسلان: ينجح واحد ويرفض الآخر409.

## الأقفال والجلسات

تتسلسل الإدارة بقفل لكل هوية تاجر/فرع حتى قبل وجود صف التفويض، ثم تعيد فحص جلسة المدير بعد الانتظار. التاجر يعيد فحص جلسة الحساب وتفويض الفرع بعد أقفال المسودة أو التكرار، وقبل نتيجة مخزنة أيضًا. يثبت فحص التفويض بقفل SHARE حتى نهاية معاملته؛ السحب المثبت قبل استئناف طلب ينتظر قفل المسودة يؤدي إلى403 ولا كتابة. إذا اكتمل طلب مخول أولًا، ينتظر السحب نهايته؛ لا تلغي العملية أعمالًا مثبتة بأثر رجعي.

لا يبطل سحب فرع كل جلسات التاجر، ولا يزيل فروعه الأخرى. إعادة منح صريحة لاحقة تسمح بالصلاحية الحالية؛ لا يعد هذا النظام epoch لإبطال الطلبات عبر سحب ثم إعادة منح. قراءة/تعديل مسودات وصور المرحلةA محمية؛ لا تدعي هذه الإضافة تغطية صلاحيات مخزون أو مالية مستقبلية.

انقطاع HTTP قبل COMMIT يعيد المعاملة كاملة، وبعد COMMIT تحفظ النتيجة ويعيدها نفس المفتاح. لا يعاد إرسال الأمر بمفتاح جديد عشوائي عند غموض الرد.

## الأخطاء وحدود النشر

| الحالة | النتيجة |
|---|---|
| جلسة قديمة/ملغاة | 401 INVALID_SESSION |
| دور غير إداري أو فرع لتاجر آخر | 403 ACCESS_DENIED |
| حساب أو فرع غير موجود | 404 NOT_FOUND |
| صيغة/حقول زائدة/سبب ناقص | 400 INVALID_INPUT |
| مفتاح غائب | 400 INVALID_IDEMPOTENCY_KEY |
| نسخة قديمة | 409 BRANCH_VERSION_CONFLICT |
| حساب ليس تاجرًا أو منح لحساب موقوف | 409 BRANCH_TARGET_NOT_ELIGIBLE |
| بيانات مختلفة بنفس المفتاح | 409 IDEMPOTENCY_KEY_REUSED |

يبقى approve مرفوضًا409/CATALOG_POLICY_NOT_CONFIGURED، وقائمة العميل فارغة وpublicationEnabled=false. لا تغيير لسعر البيع أو الضمان أو حساب7291، ولا فتح البيع من المسودات.

## الترحيل والرجوع

التسلسل في قاعدة اختبار: schema.sql ثم security.sql ثم http.sql ثم accounts.sql ثم catalog_drafts.sql ثم branch_permissions.sql. يختبر suite فشلًا متعمدًا قبل COMMIT يحفظ الصف السابق، ثم الترحيلة السليمة تحفظ التفويض السابق active/v1.

لا تطبق الترحيلة على إنتاج بهذا التفويض. عند رجوع نسخة الخادم احتفظ بالترحيلة وبفاحص active الجديد؛ حذف أعمدة active/version أو إعادة دالة branch_access القديمة يعيد صلاحيات مسحوبة. عطل catalog.enabled عند الحاجة إلى وقف المسارات، ولا تعد schema أقدم فوق بيانات أحدث. قبول نسخة إنتاج واستعادتها يخضع لخطة BACKUP_AND_RECOVERY واختبار استعادة معزول؛ هذا الاختبار ليس دليل نسخ/PITR.
