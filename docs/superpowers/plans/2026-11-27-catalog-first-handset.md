# خطة تنفيذ أول مسار للكتالوج

> **For agentic workers:** REQUIRED SUB-SKILL: استخدم superpowers:executing-plans عند تفويض التنفيذ، مهمة واحدة مع تحققها في كل مرة. جميع الخطوات أدناه مخططة وليست منفذة.

**Goal:** إضافة جوال من تاجر مخول، مراجعته إداريًا، ثم نشره باسم مقطوب وربطه بمسار الشراء، دون افتراض سياسة سعر أو ضمان أو ترحيل محاسبي غير محسومة.

**Architecture:** تبنى المسودات والنسخ والمراجعة الخاصة أولًا، دون إنشاء صنف منشور أو كمية قابلة للبيع. بعد قرارات السعر والضمان يضاف الاعتماد الذري والنشر والقراءة العامة. ربط حسابات الأستاذ والتقريب مسار منفصل لا يغيّر معنى الكمية التشغيلية أو ملكية البضاعة.

**Tech Stack:** Node.js HTTP وpg وPostgreSQL16.16 وCI الموجود، مع الحفاظ على التوافق مع Node22 وبيئة الاختبار المحلية.

**Spec:** [تصميم الكتالوج](../../design/CATALOG_FIRST_HANDSET.md)، و[لغة المجال](../../../GLOSSARY.md)، والمهمة09 في EXECUTION_PLAN.md. المتطلبات المرتبطة R01 وR03 وR04 وR08 وR10 في PROJECT_GUIDE.md.

**الحالة:** خطة فقط، 27 نوفمبر 2026، على فرع codex/catalog-design. طلب المستخدم يصرح بالتخطيط دون تنفيذ. «قابل للبدء» تعني مستقلًا عن رد الشركة ويمكن تنفيذه عند تفويض لاحق، ولا تعني أن التنفيذ بدأ أو أن مقترحات التصميم اعتُمدت.

## Global Constraints

- العميل Android/iOS، التاجر Android/iOS/Windows، الإدارة Windows فقط، والمندوب Android؛ لا واجهة ويب.
- التاجر من الجلسة، والفرع يحتاج تفويضًا صريحًا. يعاد فحص الجلسة بعد أقفال الأعمال وقبل إعادة نتيجة مخزنة.
- نسخة مرسلة ثابتة، expectedVersion وexpectedRevision للتغييرات الحساسة، ومنع تكرار مرتبط بالهوية والعملية والمورد وبصمة المدخلات.
- بضاعة التاجر merchant_owned. لا قيد مالي ولا مستحق ولا زيادة في أصل مخزون مقطوب بسبب إنشاء المسودة أو نشر العرض.
- لا صور عامة أو بطاقات عميل قبل اعتماد النشر؛ المسودة لا تدخل eligible_offer ولا quote/create.
- الأولوية المقترحة لأول شريحة هي جوال جديد وYER. لا يستخدم ذلك لإقرار دعم المستعمل أو العملات الأخرى؛ يؤكد نطاق الشريحة قبل التنفيذ.
- الملف المحاسبي الأصلي خاص، ولا يرفع إلى Git. التوضيح المنتظر لحساب7291 لا ينسخ فوق قرار الشركة السابق أو يطبق تلقائيًا.
- لا إنقاص للاختبارات77 الحالية أو حد CI الأدنى، ولا تعطيل فحص لإظهار النجاح. اختبارات الحارس الحالية15 مستقلة عن عدد حالات PostgreSQL.
- كل خطوة تطبيق لاحقة على قاعدة تجريبية جديدة، دون حذف مخزون أو طلبات أو قيود سابقة، ودون نشر أو مخاطبة مزود دفع.

**مثال قبل رد الشركة:** التاجر يحفظ مواصفات الجوال وصوره وسعر توريده54,000 وكمية1، ويرسله للمراجعة. الإدارة تقرأه وتطلب صورة أو تصحح المطابقة عبر طلب تعديل. يبقى السعر المقترح للعميل والضمان النهائي غير محسومين، ولا يظهر الجوال للعميل أو يضاف مخزون قابل للحجز.

## Review Focus

1. تاجر يزوّر merchantId أو branchId، أو يعاد إرسال طلبه بعد إبطال جلسته: رفض قبل أي أثر؛ تملك A2 وA3 اختبار ذلك.
2. سحب نسخة أو استبدالها بينما المدير ينتظر القفل: لا اعتماد نسخة قديمة ولا فقد تعديل؛ تملك A3 ثم B1 السباقين.
3. تكرار الطلب أو ضياع الرد ثم إعادته من جهازين: مسودة/قرار/كمية واحدة؛ تملك A3 وB1 الفحص قبل التثبيت وبعده.
4. صورة خاصة، رابط مورد، أو بيانات وصفية تكشفه: لا تنزيل للعميل ولا اشتقاق عام غير مراجع؛ تملك A4 وB1 وB2 الفحص.
5. مورد أرخص بضمان مختلف أو سعر تغير أثناء الاختيار: لا استبدال ضمان العميل أو سعر طلب محفوظ بصمت؛ تملك B0 وB2 اختبارات السياسات المعتمدة.

## المرحلة A — مستقلة عن أجوبة الشركة

### A1 — تثبيت عقد المسودة وحالات التوقف

**Files:** إنشاء docs/design/CATALOG_API.md؛ الرجوع للتصميم الحالي وbackend/server.mjs.
**Interfaces:** عمليات draft/create وdraft/update وdraft/read وdraft/submit وdraft/withdraw وreview/list وreview/decision. الإنشاء يرسل branchId ومواصفات وصورًا مرجعية وسعر توريد وكمية؛ لا merchantId ولا rate ولا سعر بيع مفروض. سعر العميل وسياسة الضمان المعتمدة ليسا شرطًا لحفظ مسودة.

- [x] تثبيت allowlist لكل طلب واستجابة، وقاعدة مبلغ التوريد النصي العشري والكمية الصحيحة الموجبة وexpectedVersion/expectedRevision.
- [x] تثبيت حدود الرفع التقنية المقترحة لأول شريحة: JPEG/PNG، حد5MiB لكل أصل و10 صور لكل نسخة، مع إمكانية ضبطها من إعداد الخادم. هذه اختيارات هندسية مقترحة في الخطة وليست شروط شركة تجارية.
- [x] فصل وصف الضمان الذي يقترحه التاجر داخليًا عن warrantyPolicyVersionId المعتمد، دون اعتبار نص التاجر ضمانًا صالحًا للنشر.
- [x] تثبيت أن submit يرسل نسخة للمراجعة الداخلية، ويمكنه إظهار missingDependencies، لكنه لا يوهم التاجر بالنشر أو يحمل نقص قرار الشركة كخطأ في المنتج.
- [x] توثيق رفض قرار approve أثناء غياب سياسة نشر مكتملة بـ409 ورمز CATALOG_POLICY_NOT_CONFIGURED المقترح، دون حفظ حالة approved أو أي كمية. تبقى request_changes وreject وwithdraw متاحة بشروطها.
- [x] مراجعة العقد والصلاحيات قبل مهمة المخطط. الرموز والأسماء الفنية اختيارات تنفيذ مقترحة، لا قرارات شركة مالية.

**قبول A1:** يمكن وصف كل طلب ونتيجته وسبب رفضه دون افتراض سعر بيع أو ضمان أو7291. لا تعني مراجعة العقد تنفيذ endpoint.

### A2 — تخزين المسودات وتفويض الفروع بأمان

**Files:** إنشاء catalog_drafts.sql وcatalog_drafts.cjs؛ تعديل run-tests.mjs لاحقًا.
**Interfaces:** catalog.submission وsubmission_revision وreview_decision وaudit_event وpurchase_api.principal_branch. دالتا دخول محدودتان مقترحتان catalog_read(operation,data,token_hash) وcatalog_write(operation,data,token_hash,request_key,fingerprint)، تعيدان body أو status/body، وتستخدمان الهوية الفعلية.

- [x] كتابة اختبار PostgreSQL يفشل قبل وجود الدوال: تاجر أ يحفظ مسودة في فرعه، وتاجر ب أو فرع غير مخول يعاد رفضه، ولا صفوف في مخزون/طلبات/قيود جديدة.
- [x] إضافة الترحيلة الإضافية فقط بعد accounts.sql، مع سحب صلاحيات PUBLIC وعدم منح المستخدم تعديل الجداول مباشرة.
- [x] جعل نسخة الإرسال ثابتة، ومراجع الفرع/التاجر متطابقة، وملكية المسودة غير قابلة للنقل من جسم طلب لاحق.
- [x] إضافة منع التكرار والتدقيق داخل نفس المعاملة؛ نفس المفتاح والنية نفس النتيجة، ونفس المفتاح مع بيانات مختلفة409.
- [x] اختبار تطبيق الترحيلة على نسخة تجريبية من مخطط الشراء الحالي ببياناته المصطنعة. مقارنة عدد الطلبات والقيود والمخزون قبلها وبعدها؛ لا إعادة إنشاء لجداول الشراء.
- [x] تشغيل حالات A2 عبر مشغّل الاختبارات الحالي حتى تنجح، ثم تجهيز commit محدد الملفات ومراجعة ضمن فرع التنفيذ عند تفويضه.

**قبول A2:** حفظ وقراءة معزولان ونسخ وتدقيق صحيحة، دون إنشاء sku منشور أو stock أو offer أو ترحيل مالي. تجربة قاعدة اصطناعية لا تثبت استعادة إنتاج؛ تبقى خطة النسخ المرجع عند اعتماد بيئة مشتركة.

### A3 — HTTP للمسودة والمراجعة الداخلية

**Files:** إنشاء backend/catalog.mjs؛ تعديل server.mjs وcatalog_drafts.cjs.
**Interfaces:** createCatalog({gateway,actorPool,configuredLogins}) يعيد handleCatalog(request,response,{requestId,readBody}) بأسلوب محول auth الحالي. ترجع null للمسارات غير التابعة له. يستخرج هوية الاتصال من Bearer الموثق عبر gateway، ويتحقق من configuredLogins، ثم يربط المسارات بدوال A2؛ لا يقبل هوية اتصال أو SQL حرًا من العميل.

- [x] كتابة حالات HTTP الفاشلة أولًا: إنشاء/تعديل/إرسال/قراءة/سحب، وقائمة مراجعة للإدارة، ثم request_changes وreject مع السبب.
- [x] تطبيق الحقول والصلاحيات من A1، وعدم إتاحة قرار نشر عبر حقل state من العميل أو التاجر.
- [x] اختبار إبطال الجلسة أثناء انتظار القفل للخروج من الجميع وتغيير الكلمة والإيقاف وإعادة التفعيل، باتباع نمط accounts.cjs.
- [x] اختبار جهازين يرسلان نفس الإنشاء أو القرار، ثم فقد الرد قبل COMMIT وبعده، مع مسودة وقرار واحدين.
- [x] اختبار سباق السحب مع قرار المراجعة، ورفض expectedVersion قديم دون كتابة جزئية.
- [x] تثبيت بوابة approve الموقوفة باختبار409 وعدم تغير حالات النشر والمخزون والمال. لا تستعمل قيمة ضمان أو سعر مؤقتة كاختبار نجاح إنتاجي.
- [x] تشغيل PostgreSQL/HTTP الحقيقيين وتسجيل النتائج وتجهيز commit ومراجعة لهذه المهمة عند التنفيذ.

**قبول A3:** مسار التاجر إلى المراجعة الداخلية يعمل، ولا يمكن تجاوزه إلى نشر قبل استيفاء قرارات الشركة.

### A4 — ملفات الصور الخاصة

**Files:** إنشاء backend/catalog-media.mjs وcatalog_media.cjs؛ إضافة media_asset وربط النسخة ضمن catalog_drafts.sql.
**Interfaces:** تسجيل أصل خاص يعيد assetId مبهمًا؛ قراءة/إرفاق الأصل تتطلب هوية مالكه أو المراجع المخول. لا يقبل body مسار تخزين أو URL مورد حرًا بدل مرجع أصل مملوك.

- [x] كتابة حالات رفض لتاجر آخر وعميل ومندوب يطلبون تنزيل الأصل أو إرفاق assetId لا يملكونه.
- [x] تطبيق حدود A1 للتنسيقات والحجم والعدد قبل كتابة المعالج، دون استعمالها لحسم سياسة ضمان أو تسعير.
- [x] تخزين الأصل خارج المستودع بمفتاح يولده الخادم، وحفظ بصمته وحالته وربطه بالنسخة. رفض مسارات traversal والملف المتنكر كصورة، وعدم تقديم مجلد التخزين كمسار static.
- [x] إبقاء الحالة خاصة وغير جاهزة للنشر العام حتى تجهيز المشتق وفحص محتواه في B1. لا يوصف مجرد حفظ metadata بأنه معالجة صور كاملة.
- [x] تشغيل اختبارات الملفات المصطنعة وHTTP وحفظ دليل الرفض والتنظيف، دون رفع أصل خاص أو بيانات المصدر إلى Git.

**قبول A4:** صور مسودة خاصة يمكن مراجعتها داخليًا، دون روابط عامة أو كشف التاجر.

### A5 — قبول المرحلة المستقلة

**Files:** run-tests.mjs وdocs/verification/CATALOG_HTTP.md؛ لا تغيير لقاعدة بيع أو محاسبة.

- [ ] إدراج حالات الكتالوج الجديدة والتحقق أن expectedCount يتضمنها، مع بقاء77 حالة أصلية.
- [ ] تشغيل `node --test scripts/ci/run-tests.test.mjs` ثم `node scripts/ci/run-tests.mjs`، بعد تثبيت الاعتماديات عند الحاجة.
- [ ] إثبات أن كل طلبات المسودة/المراجعة لم تغير purchase.stock أو offer أو payable أو journal أو posting، ولم تضع عرضًا في قائمة المؤهلين للبيع.
- [ ] مراجعة مستقلة للفرع وطلب مراجعة، ثم متابعة GitHub CI. لا تجاوز حماية main أو إعلان نجاح اختبارات لم تنفذ.

**نهاية A:** يمكن عرض مثال عملي داخلي عبر HTTP من إنشاء المسودة حتى رد الإدارة، مع بقاء المنتج غير منشور. هذا تقدم مقبول مستقل وليس اكتمال الكتالوج العام.

## المرحلة B — بعد سعر البيع والضمان

### B0 — تحويل رد الشركة إلى شروط قابلة للاختبار

**Files:** تحديث محضر القرارات والتصميم وCATALOG_API.md وهذه الخطة، دون استبدال القرارات السابقة بصمت.

- [ ] تسجيل قاعدة سعر البيع ومن يملك تعديلها، وأساس العمولة ومعالجة فرق البيع إذا وجد، ومثال أرقام مصادق عليه.
- [ ] تسجيل الضمان: المدة والشروط والاستثناءات وجهة الالتزام والتكلفة، وهل يتوحد لنفس بطاقة الصنف أو يختاره العميل كخيار مستقل.
- [ ] تأكيد نطاق الشريحة الأولى: جديد/YER، وتسجيل أي توسعة كعمل إضافي بدل إدخالها ضمن A تلقائيًا.
- [ ] تحديث اختبارات B1 وB2 أدناه بقيم الشركة الفعلية. لا يفترض المثال الحالي54,000 أو10% أو ضمان12 شهرًا سياسة عامة.

**البوابة:** لا تنفيذ لقاعدة السعر أو ضمان النشر قبل B0. إذا ردت الشركة على السعر فقط، يمكن حسم حساب السعر واختباره، لكن لا يفتح اعتماد النشر دون الضمان، والعكس صحيح.

### B1 — الاعتماد الذي ينشر العرض مرة واحدة

**Files:** catalog_publication.sql وcatalog_publication.cjs وcatalog-media.mjs وCATALOG_API.md.
**Interfaces:** إضافة sku_profile وwarranty_policy_version وmerchant_terms_version وlisting، وتفعيل decision=approve بشروط B0. يجهز المشغل مراجع الاتفاقات المعتمدة؛ لا بناء نظام عقود كامل.

- [ ] كتابة اختبار فاشل لاعتماد نسخة محددة: ربط صنف مطابق أو إنشاؤه، listing واحد وstock واحد بالكمية الافتتاحية وoffer واحد من شروط معتمدة، بلا قيد مالي.
- [ ] تجهيز مشتق الصورة العام بمحتوى وبيانات وصفية مراجعة؛ يجب أن يكون جاهزًا قبل معاملة الاعتماد، ولا ينتظر قفل القاعدة رفعًا أو معالجة صورة.
- [ ] في معاملة واحدة، قفل الطلب والتحقق من النسخة والجلسة والشروط، ثم النشر والقرار والتدقيق والنتيجة المخزنة.
- [ ] اختبار جهازين يعتمدان نفس النسخة وفقد الرد/الإعادة: كمية واحدة فقط. وجود stock سابق للفرع والصنف يمنع إضافة initialQuantity عليه تلقائيًا.
- [ ] اختبار أن تعديل السعر/الصورة لاحقًا ينشئ نسخة عرض دون إضافة كمية. هذا لا يفتح استلام مخزون إضافي؛ تلك وظيفة المهمة10.
- [ ] اختبار توقف الاعتماد إذا سحب التاجر النسخة أثناء الانتظار أو غابت سياسة ضمان/عمولة معتمدة.

**قبول B1:** النشر صحيح ومعاداته لا تضاعف المخزون، دون تحويل بضاعة التاجر إلى أصل لمقطوب.

### B2 — بطاقة العميل وربطها بعرض السعر

**Files:** backend/catalog.mjs وcatalog_publication.sql؛ تعديل http.sql وquote_handset في schema.sql بترحيلة توافقية مدروسة؛ اختبارات catalog_publication.cjs.

- [ ] كتابة قراءة عامة ببطاقة واحدة للصنف، وجهة بيع مقطوب، ومواصفات وصور وضمان وسعر مشتق من قاعدة B0، دون حقول المورد أو كمية مخزونه الدقيقة.
- [ ] اشتقاق الأهلية من العروض المنشورة والفرع والنشاط والكمية والسياسات المعتمدة، بدل قائمة يهيئها المشغل يدويًا. لا تخترع ترتيب مفاضلة جديدًا.
- [ ] حفظ نسخة السعر والضمان اللذين قبلهما العميل مع quote وبند الطلب. عند اختلاف ضمان مورد أرخص يطبق قرار B0 بدل استبدال الضمان بصمت.
- [ ] اختبار عدم إمكانية إصدار quote لمسودة أو منتج غير منشور بمجرد معرفة skuId، ورفض تسرب المورد من JSON والصور والروابط والأخطاء.
- [ ] اختبار أن تحديث النشر أو السعر لا يعدّل طلبًا أو عرض سعر محفوظًا بأثر رجعي.
- [ ] إعادة اختبار عميلين على آخر قطعة من منتج أضافه التاجر عبر HTTP بالفعل، بدل الاقتصار على منتج fixtures.

**قبول B2:** يقرأ العميل بطاقة صحيحة ويصل إلى حجز آمن؛ هذه ليست واجهة تطبيق هاتف أو Windows منفذة.

### B3 — قبول الشريحة من الإضافة حتى التسليم

- [ ] تشغيل تاجر→مراجعة→اعتماد→قراءة عميل→quote→حجز→دفع تجريبي→تسليم، مع أرقام الشركة المعتمدة وفحص مستحق التاجر والعمولة.
- [ ] تكرار طلبات النشر والحجز والدفع والتسليم وفقد الرد والتحقق من أثر واحد لكل عملية ومن عدم تغير الطلبات القديمة.
- [ ] تشغيل المجموعة القديمة والجديدة وحارس CI ومراجعة مستقلة وطلب مراجعة للمرحلة.

## المرحلة C — تنتظر توضيح7291 والمحاسب

هذه مرحلة مالية منفصلة؛ لا تعيد تشكيل مسودات الكتالوج بسبب تأخرها.

- [ ] تأكيد: هل7291 يقبل الترحيل وقت الدفع أم الإقفال فقط؟ إذا كان للإقفال، ما الحساب الوسيط المعتمد وكيف يسوى؟
- [ ] تحديد سقف التقريب ووحدته: فاتورة أو فترة، ومعالجة التجاوز، وربط الحسابات الرقابية بالأبعاد اللازمة.
- [ ] بعد الرد فقط، تحديث تصميم mapping المالي واختبار المثال: إجمالي11,832.50 ودفع11,832 وفرق0.50، وفق الحساب الذي يقره المحاسب.
- [ ] تثبيت مثال الخصم الأكبر إن بقي معتمدًا: دفع11,800 يتضمن0.50 تقريبًا و32 خصمًا ممولًا، دون تحميل كامل32.50 على حساب التقريب.

**بوابة C:** حسم7291 وحده لا يكفي لإعلان مطابقة دفتر التجربة للدليل كاملًا؛ يلزم اعتماد mapping الأسماء التجريبية وبقية الحسابات ذات الصلة أيضًا. هذا لا يجعل المهمة09 مسؤولة عن تنفيذ نظام المحاسبة الكامل.
