# تنفيذ سجل نسخ المسودة والمقارنة

النطاق المفوض R03 والمرحلةA، على codex/catalog-revision-history منmain/9adb6d7. قراءة التاريخ والمقارنة فقط؛ لا نشر أو بيع أو اعتماد سعر/ضمان/7291، ولا استرجاع نسخة قديمة كعملية كتابة.

## التصميم

- GET /v1/{merchant|admin}/catalog/submissions/{id}/revisions: قائمة بيانات النسخ وأوقات الحفظ وملاحظة المراجعة لكل نسخة، مرتبة برقمrevision تصاعديًا. limit من1 إلى100 افتراضي50، وcursor رقم آخرrevision كنص. لا محتوى كامل في القائمة.
- GET .../revisions/{revision}: المحتوى المحفوظ للنسخة المحددة، ووقت الحفظ وقرار مراجعتها إن وجد. لا يستنتج تاريخ حالة لم يسجل في القاعدة.
- GET .../compare?from=1&to=2: النسختان مع المحتوى ومراجعاتهما، وقائمةchanges مرتبة باسم الحقل معbefore/after وbeforePresent/afterPresent، وصورmedia.added/media.removed. المقارنة عكسية أيضًا؛ النسخة نفسها تعطيchanges فارغة. أرقام المقارنةrevision لاversion.
- كل استجابة تعرفsubmissionId/branchId وversion/currentRevision/state الحالية منفصلة عن المحتوى التاريخي، وpublicationEnabled=false. لا معرفاتLOGIN داخلية أوbytes صور أوروابط عامة.
- الإدارة الحالية فقط على مساراتadmin؛ وعلىmerchant صاحب المسودة وحده ضمن المنشأة والفرع المخول. الزميل في المنشأة والتاجر الآخر والعميل والمندوب والخدمة مرفوضون. لا اختيار للدور أو المنشأة من الجسم/الاستعلام.
- القفل SHARE على المسودة، ثم التفويض الحالي للفرع، ثم إعادة فحص الجلسة بعد الانتظار. المالك والمنشأة يفحصان من الجلسة الحالية؛ الإدارة لا تحتاج تفويض فرع تجاري. السحب المثبت قبل استئناف القراءة403؛ إبطال الجلسة401. الأقفال تبقى حتىCOMMIT وتؤخر الكاتب المتزامن بدل خلط النسخ.
- قارئ النسخة الخاصSTABLE ومقارنة واحدة متسقة. التاريخ immutable أصلًا؛ لا حذف أو تغيير لسجل قديم. الصفحات ليست snapshot ثابتة بين الطلبات، ويمكن أن تظهر نسخ جديدة في صفحة لاحقة.
- ترحيلةcatalog_history.sql بعدmerchant_draft_list.sql تضيف دوال فقط، مع إلغاءPUBLIC EXECUTE ومنح دالةAPI المحددة للمشغل. اختبار فشل قبلCOMMIT يحفظ البيانات السابقة؛ لا إنتاج أوPITR.

## التنفيذ والتحقق

- [x] اختبار HTTP/PostgreSQL جديد catalog-history-http يفشل404 قبل إضافة المسارات، دون حذف84 حالة سابقة.
- [x] إضافة catalog-history.mjs لتحقق الاستعلامات والمسارات، وربطها بالقارئpurchase_api.catalog_history(text,jsonb,text).
- [x] إضافة الترحيلة والقارئSTABLE وعزل الأدوار والمالك والفرع، مع rollback معزول.
- [x] اختبار نسختين أُنشئتا عبر HTTP، والمراجعة والصور، والمقارنة في الاتجاهين وللنسخة نفسها، والمفقود والمدخلات الزائدة.
- [x] اختبار أكثر من100 نسخة، والصلاحيات بين التجار وزميل المنشأة، وسحب الفرع أثناء انتظار قفل المسودة وقفل التفويض، وإبطال جلسة التاجر والإدارة أثناء الانتظار.
- [x] اختبار قراءة تمسكSHARE وكاتبHTTP ينتظرها، دون خلط بيانات القراءة بالمحتوى الجديد. مقارنة الجداول لإثبات عدم كتابةGET وثبات المخزون والمال وقفل النشر.
- [x] التحقق النهائي بعد تنظيف التشخيص وتوثيق النتائج:85/85 عبر الحارس علىPostgreSQL16.16 وHTTP، و15/15 للحارس. التنفيذ محلي فقط؛ لاcommit/push/merge ضمن هذا الطلب.
- [x] مراجعة مستقلة: تعذرت المحاولة الأولى، ثم أعيدت بطلب المستخدم واكتملت دونP1/P2 مؤكدة. راجع المراجع المصدر والصياغة والفرق؛ لم يعد تشغيلPostgreSQL بصورة مستقلة.

Ruling: تشغيل الطفل في المشغّل بصورة غير متزامنة متسلسلة — تفريغ قنوات سجلPostgreSQL يجب أن يستمر أثناء حالاتSQL السلبية. بقيت مهلة60ثانية وحد الخرج ورفض الصفر والفشل؛ لا خفض للسجلات لإظهار النجاح. [الدليل](../../verification/CATALOG_HISTORY_HTTP.md).
