# خطة إدارة صلاحيات الفروع

> تنفيذ مباشر وفق تفويض المستخدم، باستخدام superpowers:executing-plans، والاختبار أولًا والمراجعة المستقلة قبل تسليم الفرع.

**Goal:** إدارة تعرض تفويض الفروع لحساب تاجر وتمنحه وتسحبه عبر HTTP، مع رفض طلب تاجر ينتظر قفلًا إذا انتهت المعاملة بسحب الصلاحية قبل استئنافه. يبقى النشر والبيع للكتالوج الجديد متوقفين.

**Spec:** طلب المستخدم، R03 وRULES.md، وعقد المرحلةA CATALOG_API.md. لا إنشاء تجار أو فروع أو حسابات أو تغيير أدوار من هذه المسارات.

**Architecture:** ترحيلة إضافية بعد catalog_drafts.sql تحافظ على صف الصلاحية وتضيف active/version بدل الحذف عند السحب. عمليات الإدارة متسلسلة لكل حساب/فرع بأقفال ومع expectedVersion ومفتاح تكرار وتدقيق. catalog.branch_access يفحص active بعد انتظار الأقفال. لا ترحيلة إنتاج أو بيانات حقيقية.

## العقود المختارة

- GET /v1/admin/accounts/{accountId}/branches يعرض فروع منشأة الحساب وصلاحياته، بصفحات100 ومؤشر branchId. الحساب المستهدف merchant فقط، وتستمد منشأته من هويته الموثقة في القاعدة.
- POST .../branches/{branchId}/grant أوrevoke بجسم expectedVersion وreason. قبل أول صف النسخة0. كل قرار ناجح جديد يزيد النسخة؛ إعادة نفس المفتاح والنية تعيد نتيجة العملية الأصلية دون تطبيقها مجددًا.
- الحالة المخزنة هي المرجع الحالي: إعادة نتيجة منح قديمة لا تلغي سحبًا أحدث. مفتاح جديد بنسخة قديمة يرفض409. قراءة القائمة ترجع الحالة الحالية.
- منح حساب موقوف أو هوية غير نشطة مرفوض، وسحب تفويضه يظل متاحًا للتنظيف. فرع خارج المنشأة403، ومعرف غير موجود404، والحقول الزائدة400.
- لا يستطيع مستخدم التاجر أو العميل أو المندوب أو الخدمة إدارة التفويضات. الإدارة تعيد فحص جلستها بعد انتظار أقفال العملية حتى عند إعادة نتيجة مخزنة.
- الصلاحية المنزوعة تبقى inactive في صف ذي نسخة وتدقيق. منح جديد صريح لاحق يجعل الصلاحية الحالية فعالة؛ هذه المهمة لا تلغي جميع جلسات التاجر لمجرد تغيير تفويض فرع.
