# مهارة عقود الواجهات البرمجية والعزل — مقطوب

توفر هذه المهارة إرشادات تشغيلية ومعايير هندسية لتصميم ومراجعة وتأمين عقود واجهات برمجة التطبيقات (APIs) ونماذج تبادل البيانات (DTOs) بين الخادم والتطبيقات الأصلية لمنصة مقطوب، تطبيقًا للقواعد R01، R02، R03 والقواعد 6، 8، 11 في `RULES.md`.

## 1. متى تُستخدم المهارة

تُفعّل هذه المهارة إلزاميًا عند:
- إنشاء أو تعديل مسارات الخادم (Endpoints) أو مواصفات OpenAPI/Swagger.
- تصميم أو تحديث حزمة عقود العميل المشتركة (`packages/api_client`).
- تحديد نماذج الطلب والاستجابة (Request/Response DTOs) لأي وحدة عمل.
- إعداد طبقات التحقق من الصلاحيات (Authorization) وعزل المنشآت (Tenant Isolation).
- مراجعة أمان الواجهات ومنع تسريب بيانات الموردين للعملاء.

## 2. القنوات المعتمدة وحدود التصميم

تلتزم جميع الواجهات بحدود القنوات المعتمدة حصرًا، مع المنع التام لأي واجهات أو بوابات ويب:
- **تطبيق العميل**: Android وiOS (هوية مقطوب الموحدة فقط).
- **تطبيق التاجر**: Android وiOS وWindows Desktop.
- **تطبيق الإدارة**: Windows Desktop فقط.
- **تطبيق المندوب**: Android فقط.
- **ممنوع تمامًا**: إنشاء واجهات ويب، متجر ويب، أو لوحة إدارة ويب لأي دور. وجود بروتوكول HTTPS لا يعني إتاحة صفحات ويب.

## 3. خطوات العمل الفنية

1. **عزل نماذج البيانات (DTO Data Leak Prevention)**:
   - **واجهة العميل (Customer API)**: يُمنع منعًا باتًا تسريب هوية التاجر المورد (`merchantId`, `storeName`)، تكلفة الشراء، أو نسبة عمولة المنصة في أي استجابة موجهة للعميل أو في استعلامات الكتالوج والطلب. العميل يتعامل مع مقطوب كواجهة وحيدة.
   - **واجهة المندوب (Courier API)**: تعرض فقط بيانات مهمة التوصيل، العنوان، ونوع الاستلام/التسليم، مع حجب تفاصيل التوريد وسجلات الحسابات الداخلية للتاجر.
   - **واجهة التاجر (Merchant API)**: مقيدة بحدود المنشأة (`tenant_id`) والفروع المخصصة للمستخدم؛ لا تظهر بيانات تجار آخرين مطلقًا.

2. **التحقق من الصلاحيات وحالة الحساب على الخادم (Zero Client Trust)**:
   - لا يثق الخادم بأي دور أو هوية منشأة أو سعر أو حالة دفع مرسلة من التطبيق.
   - يتم استخراج هوية المستخدم الأساسية من جلسة أو رمز موثق، ثم يتحقق الخادم من:
     - العضوية والصلاحيات الفعلية الحالية في قاعدة البيانات أو مخزن الجلسات.
     - حالة الحساب (نشط، موقوف، معطل).
     - الصلاحية الحالية للوصول إلى السجل المطلوب والفرع المحدد.
   - **تجنب ادعاءات الرمز القديمة**: لا تُعتمد ادعاءات الرمز (`claims` داخل JWT) كمصدر وحيد ومطلق للصلاحيات الحساسة، بل يُعاد التحقق من الوضع الحالي للحساب والصلاحية عند تنفيذ العمليات المحمية لمنع استغلال رموز منتهية الصلاحية الإدارية قبل انتهاء زمن الرمز التقني.
   - التحقق من ملكية السجل ومستوى الوصول قبل أي قراءة أو تعديل، ورفض الوصول المتقاطع بين المنشآت بحسب سياسة العقد (مثل `403 Forbidden` أو `404 Not Found`).

3. **منع تكرار الأثر المالي والتشغيلي (Idempotency)**:
   - **ضرورة منع التكرار**: الالتزام الوظيفي الصارم بأن أي عملية تعديل حساسة (إنشاء طلب، محاولة دفع، صرف مستحق، استهلاك بطاقة، تعديل كميات) لا ينتج عن تكرار إرسالها أي أثر مضاعف.
   - **رأس `Idempotency-Key` كاقتراح تصميم**: استخدام رأس طلب مثل `Idempotency-Key` لعمليات التطبيقات هو **مقترح تصميم تقني** يخضع للاعتماد النهائي ضمن توثيق العقد؛ ويجوز للتصميم المعتمد تحديد اسم الرأس وآلية توليده وتخزينه.
   - **إشعارات المزودين الخارجيين (Webhooks)**: إشعارات المزودين لها معرفات أحداث مستقلة (`provider_event_id`) وآليات تحقق وتوقيع خاصة بها (Signatures/HMAC) أو استعلام معاكس عن الحالة، ولا تخلط مع رؤوس منع التكرار الخاصة بتطبيقات المستخدمين.

4. **إدارة عروض الأسعار (Quote Lifecycle)**:
   - إنشاء الطلب يعتمد على عرض سعر (`quote`) سارٍ ومولد ومحفوظ في الخادم متضمنًا الأسعار وسعر الصرف المحسوب، ولا يعتمد على مبالغ أو أسعار مرسلة من العميل.

5. **نماذج الأخطاء كأمثلة تصميمية**:
   - صيغ الأخطاء البرمجية ورموزها الميدانية هي **أمثلة ومقترحات تصميم** حتى اعتماد العقود رسميًا، وليست قرارات قطعية مفروضة مسبقًا. تشمل الأمثلة المقترحة:
     - نفاذ الكمية المطلوبة (مثلًا: `INSUFFICIENT_STOCK`).
     - انتهاء صلاحية عرض السعر (مثلًا: `EXPIRED_QUOTE`).
     - عدم صلاحية كود البطاقة (مثلًا: `INVALID_CARD_CODE`).
     - عدم توفر توصيل مباشر للعنوان (مثلًا: `STORE_DELIVERY_UNAVAILABLE`).
   - تعتمد أسماء الأدوار (كأدوار قاعدة البيانات أو أدوار النظام) كأمثلة استرشادية لحين اعتماد هيكل الصلاحيات النهائي.

## 4. معايير التحقق والأدلة (Verification Criteria)

- **فحص العزل السلبي (Cross-Tenant Negative Test)**:
  - محاولة مستخدم التاجر A قراءة أو تعديل طلب أو مخزون يخص التاجر B: النتيجة الحتمية رفض الطلب وتسجيل محاولة وصول غير مصرح بها.
- **فحص منع تسرب البيانات (Data Leak Test)**:
  - فحص استجابات JSON لواجهة العميل والتأكد من غياب حقول التكلفة واسم وهوية المورد وعمولات المنصة.
- **فحص التحقق المحدث للصلاحيات**:
  - اختبار سحب صلاحية مستخدم أو إيقاف حسابه والتحقق من رفض طلبه فورًا حتى لو كان الرمز السابق ساري المفعول زمنيًا.
- **التوافق بين المنصات**:
  - فحص سلامة عقود Dart المشتركة وقدرتها على العمل بسلاسة على بيئات Flutter الأصلية المعتمدة (Android, iOS, Windows).

## 5. حدود الصلاحية (Authority Boundaries)

- يمنع إنشاء أي واجهات HTML/Web أو صفحات متصفح تحت أي مبرر.
- تفاصيل رؤوس العقود ورموز الأخطاء تظل مقترحات فنية حتى يصدر اعتمادها في مواصفة OpenAPI أو ADR معتمد.
- لا تعتبر مواصفة API جاهزة بمجرد كتابتها في ملف توثيق؛ يلزم فحص مساراتها واختبارات التحقق الخاصة بها عند بدء التطوير.
